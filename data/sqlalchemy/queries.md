In modern SQLAlchemy (version 2.0+), database querying centers around construct-driven declarative SQL statements rather than the legacy `session.query()` interface. The core foundation of data retrieval is the `select()` construct, which programmatically builds abstract syntax trees representing SQL queries. By instantiating `select(User)`, developers construct an un-executed query object that encapsulates target tables, columns, and relations. This paradigm unifies the Object-Relational Mapping (ORM) layer and Core expression language under a single syntax, ensuring that queries are built deterministically, maintain strict type safety, and remain completely database-agnostic across engines such as PostgreSQL, SQLite, and MySQL.

Filtering retrieved records is accomplished primarily through the `.where()` clause, which accepts Python expressions that SQLAlchemy translates into SQL conditionals. Python's native operators—such as `==`, `!=`, `<`, `>`, and `~`—are overridden on ORM-mapped column attributes to construct SQL expression objects rather than standard boolean outputs. Complex multi-condition filters can be composed by passing comma-separated arguments to `.where()` (which defaults to logical `AND`), or by explicitly employing boolean combinators such as `and_()`, `or_()`, and `not_()`. Additionally, specialized column methods like `.like()`, `.ilike()`, `.in_()`, `.between()`, and `.is_(None)` enable granular pattern matching, set evaluation, range filtering, and nullability checks without writing raw SQL.

Relational queries spanning multiple models rely on explicit or inferred join mechanics via the `.join()` and `.outerjoin()` methods. When relationships are defined using ORM `relationship()` attributes, SQLAlchemy automatically infers the underlying foreign key join conditions (e.g., `select(User).join(User.addresses)`), though explicit conditional clauses can be supplied manually via `.join(Address, User.id == Address.user_id)`. For statistical and group-based operations, SQLAlchemy exposes the `func` module, which acts as a dynamic factory for native SQL aggregate functions such as `func.count()`, `func.sum()`, `func.avg()`, `func.max()`, and `func.min()`. Grouping datasets across aggregated fields is executed using `.group_by()`, while post-aggregation filtering relies on the `.having()` clause.

Once constructed, statement objects are passed to the database through the active ORM `Session` using either `session.execute(stmt)` or `session.scalars(stmt)`. The `execute()` method returns a tabular `Result` object containing row tuples, whereas `scalars()` automatically unwraps the primary entity from each row, returning direct instances of the mapped Python class. Result sets can be consumed using execution methods like `.all()` to return a complete list, `.first()` to obtain the initial result or `None`, `.one()` to enforce that exactly one match exists, or `.one_or_none()`. To prevent latency bottlenecks such as the $N+1$ query problem during relationship traversal, developers utilize relationship loader options like `selectinload()` (which issues an optimized secondary `IN` query) or `joinedload()` (which uses an eager SQL `LEFT OUTER JOIN`), giving full control over memory overhead and execution efficiency.
